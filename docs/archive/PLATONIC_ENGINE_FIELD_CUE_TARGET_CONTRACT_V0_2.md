# PlatonicEngine Field-Cue Target Contract v0.2

Audience: future agents, mothership successors, planners, prompt-writers, Codex workers, auditors, and any lieutenant working on PlatonicEngine’s field-cue / generated-site legibility pivot.

Status: project-government contract. This is not a Codex prompt, not a backlog, not a UI branch plan, not a topology plan, and not a claim that the current repo already implements the whole object described here. It is a binding target horizon plus a narrow authorization for FieldCueV0 work.

Authority context: this document sits under the PlatonicEngine Ground Plan, the Field Layer Appendix, the Field Source Profile and Quark-Coherent Child Inheritance Contract, the Event Legibility Pivot Charter, and the Prompter Lieutenant Initiation. It does not replace them. It sharpens what the field must become answerable to after the Event Legibility Pivot.

Governing law inherited from the pivot:

```txt
event legibility before field expansion
```

Governing law added by this contract:

```txt
the field-cue is the field’s witness inside the generated-site reading
```

The field remains derived, policy-relative, non-historical, non-packet-writing, non-shape-mutating, and non-naming. The generated site remains the center. The human names.

---

## 0. Why this contract exists

The field layer has reached a threshold where it can either become useful or become an enormous avoidance machine.

The project already has serious machinery: source domains, generated-child source inclusion, complex field sampling, closed-surface atlas behavior, profile-aware source policy, Quark child inheritance, child degeneracy diagnostics, candidate feature reports, route/gate candidates, support/region candidates, evidence stability, runtime boundaries, view models, markers, and UI exposure.

Machinery is not enough.

The human does not need a wall of field diagnostics. The human does not need a decorative scalar overlay. The human does not need a field cockpit that displays everything the system happens to compute.

The human needs the field to help answer a precise question:

```txt
What does this generated site inherit as a field source,
and how does that source participate in the surrounding field-world,
so that I can better judge what concept may dwell here?
```

A field-cue is the answer-form for that question.

A field-cue is not a reduction of the field’s ambition. It is the form in which the field becomes useful to the project’s central act: the naming, rejection, suspension, or revision of generated conceptual dwellings.

## 1. Authority levels inside this contract

This contract contains three levels of authority. Future agents must not mix them.

### 1.1 Binding target horizon

The target horizon says what a mature field-cue must eventually answer.

A mature field-cue must account for both:

```txt
child-source inheritance
field-world participation
```

It must eventually make routes, gates, loops, vortices, regions, phase transformations, supports, blockages, resonances, and field-feature neighborhoods intelligible where the field actually supports them.

This horizon is real. It is not decorative language. It is the field layer’s long demand.

### 1.2 Current authorized implementation scope

The currently authorized implementation scope is FieldCueV0.

FieldCueV0 is narrow:

```txt
one named or profile-assigned tetrahedral seed
one Ambo operation
six generated midpoint child sites
existing profile-aware field prototype
existing candidate machinery only
```

FieldCueV0 must not pretend to be the mature field-cue system. It must explicitly report which parts of the target are available, candidate-only, unsupported, degenerate, saturated, sensitive, or not yet implemented.

### 1.3 Future maturation, not current permission

Mature field-feature role profiles, confirmed field routes, confirmed gates, confirmed loops, confirmed vortices, mature regions, phase-transformation ecology, animated field behavior, and general field-cue portability are future maturation work.

They are not forbidden. They are not currently authorized merely because this contract names them.

They become branch-permissible only when they satisfy the branch permission test in this document and the Event Legibility Pivot Charter.

## 3. Core invariant

A field-cue is a site-relative field biography.

It answers two questions:

```txt
1. What field signature did this generated child inherit?
2. Once it became a source, how does it participate in the field-world?
```

The first question looks backward into birth. It concerns parent sources, projection sources, Quark channels, profile assignment, derived emission tuple, complement edge, antipodal relation, degeneracy, fallback, and unresolved states.

The second question looks outward into field ecology. It concerns where the child-source’s wave behavior travels, what carries it, what blocks it, what it feeds, what it is adjacent to, what it echoes, what it destabilizes, what phase behavior it crosses, and what field structures answer back to it.

The mature target is not satisfied by local intensity alone.

The mature target is not satisfied by Quark inheritance alone.

But FieldCueV0 may honestly say:

```txt
outward participation evidence is unavailable;
outward participation evidence is candidate-only;
outward participation evidence is saturated;
outward participation evidence is sensitive;
outward participation evidence is not useful for naming in this event.
```

Silence is forbidden. Honest unsupportedness is allowed.

## 4. What a field-cue is

A field-cue is the field witness inside a generated-site reading.

A generated-site reading may include geometry, lineage, atomic birth-law, packet/naming context, human notes, and later handoff material. The field-cue is not the whole reading. It is the field’s contribution to that reading.

A field-cue gathers field-relevant facts, inherited source structure, candidate field-world relations, caveats, visualizable behaviors, and naming pressures around one site.

For the proving event, the natural generated sites are the six Ambo midpoint children:

```txt
M_AB
M_AC
M_AD
M_BC
M_BD
M_CD
```

For each such site, the mature field-cue should eventually be able to say:

```txt
This child was born from this parent edge.
It inherited these pressures through these Quark channels.
It became this kind of source-profile tuple under this source policy.
Its emitted waves enter, fail to enter, or disturb these field structures.
It is carried, blocked, amplified, cancelled, bent, trapped, dispersed, or made ambiguous by these features.
It neighbors or answers to these routes, gates, regions, loops, vortices, support structures, phase transformations, siblings, or antipodes.
Those field features have these field-ecological roles and these evidential limits.
This produces these pressures, warnings, contrasts, and questions for human naming.
```

This is not automatic naming. This is not packet truth. This is not topology. This is field intelligibility in service of generated-site legibility.

## 6. The inheritance axis

The inheritance axis says how a generated child became a source.

For a tetrahedral Ambo child on edge `AB`, the inheritance axis should preserve, where available:

```txt
site id = M_AB
source edge = AB
parent sources = A, B
complement edge = CD
projection sources = C, D
antipodal child = M_CD
child role = shared 90-pole
inheritance grammar = tetrahedral-edge-complement-quark-inheritance-v0
Quark channels:
  A60 + C30
  B60 + C30
  A60 + D30
  B60 + D30
derived emission tuple:
  amplitude
  wave number
  phase
  attenuation
degeneracy status
fallback status
unresolved status
source policy id
profile setup id
```

This axis answers:

```txt
What did the child inherit?
From whom?
Through what channel grammar?
Under what active source policy?
What tuple was emitted?
What structure must not be erased by that tuple?
What degeneracy or instability must the human know about?
```

The numeric tuple is never the whole truth of inheritance. The tuple is the compressed emission result of a structured birth-path.

If the tuple collapses two children, hides an antipodal distinction, falls back, or becomes unresolved, the cue must say so. Degeneracy is a field fact, not an embarrassment.

The mature field-world axis should eventually account for:

```txt
nearby gates;

loops adjacent to or encircling;

phase corridors crossed;
phase transformations induced or undergone;
support structures strengthened;
support structures destabilized;
sibling-site resonances;
antipodal echoes;

```

This axis answers:

```txt
Where does this child’s field signature travel?
What blocks it?
What carries it?
What does it feed?
What does it fail to enter?
What field structures answer back to it?
What neighboring field behavior should matter to the human’s act of naming?
```

For FieldCueV0, the field-world axis may be partial. It may contain candidate references rather than mature relations. It may contain warnings rather than confident statements.

The required law is:

```txt
Do not inflate a candidate reference into mature participation.
Do not suppress participation merely because it is still candidate-only.
Do not pretend that unsupported means unimportant.
Do not pretend that possible means mature.
```

## 8. Field-semantic embedding

A mature field-cue cannot treat a gate, route, loop, region, vortex, support, or phase transformation as a raw numerical artifact forever.

A mature field feature must eventually have a field-semantic role profile.

This phrase is binding, but it must be read correctly.

Field-semantic embedding does not mean conceptual naming.

It does not mean:

```txt
the gate has a philosophical name;
the route has a concept-name;
the region has a packet;
the vortex is ontologically confirmed;
the field has named the generated site.
```

It means:

```txt
the feature has a role inside the field ecology.
```

There are therefore two semantic registers:

```txt
field-feature semantics:
  what role does this feature play inside the field-world?

conceptual naming semantics:
  what concept, if any, can dwell at the generated site?
```

The first may be system-assisted.

The second remains human-centered.

The project must not flatten field-feature role into raw measurements. It must also not mistake field-feature role for philosophical naming.

---

## 9. Evidential law for field-semantic role profiles

A field-semantic role profile is not created by vocabulary.

No agent may mature a feature merely by calling it a gate, route, loop, vortex, support, or region.

A role profile must be licensed by explicit field evidence. Such evidence may include:

```txt
sample or chart evidence;
source-family contribution behavior;
mixture / dominance / cancellation behavior;
phase behavior;
feature adjacency;
route/gate/region relation evidence;
relation to one or more generated sites;
relation to sibling or antipodal sites;
stability or sensitivity status;
known scope limits;
known unsupported gaps.
```

If those evidential relations are missing, the role profile must remain one of:

```txt
unknown;
unsupported;
candidate-only;
provisional;
rejected;
unresolved;
sensitive.
```

The field is allowed to be wild. It is not allowed to be theatrical.

A field feature that speaks must show what authorized its speech.

## 10. Maturity ladder

The field-cue system distinguishes these maturity levels.

### 10.1 Raw measurement

Raw measurements are numerical field data:

```txt
complex psi;
intensity;
phase;
contribution magnitude;
contribution ratio;
gradient;
sample position;
chart coordinate;
local adjacency.
```

Raw measurement is necessary. It is not yet humanly sufficient.

### 10.2 Candidate feature

A candidate feature is a detected structure from field data:

```txt
feature observation;
gate candidate;
route candidate;
blocked-route candidate;
support-region candidate;
high-intensity anchor candidate;
cancellation-like site candidate;
ambiguous field site candidate.
```

Candidate features are allowed. They must remain candidate-only unless matured by evidence and audit.

### 10.3 Candidate relation

A candidate relation links a generated site to a candidate feature:

```txt
near;
adjacent-to;
possibly-enters;
possibly-blocked-by;
possibly-feeds;
possibly-resonates-with;
possibly-opposes;
possibly-complements.
```

A candidate relation is not yet field-world participation. It is a possible relation awaiting stronger evidence.

### 10.4 Field-semantic role profile

A field-semantic role profile gives a feature a field-ecological role:

```txt
governs passage;
conducts pressure;
blocks route;
feeds region;
bounds region;
recirculates phase;
organizes neighborhood;
destabilizes neighborhood;
anchors intensity;
marks cancellation;
marks ambiguity.
```

A role profile requires evidence. It is still not conceptual naming.

### 10.5 Field-cue

A field-cue is the site-centered composition of:

```txt
child inheritance;
emitted source signature;
field participation or candidate participation;
field-semantic feature relations where justified;
visual/interference behavior where available;
naming pressure;
warnings;
caveats;
unsupported states.
```

Only this level is the field’s proper contribution to generated-site legibility.

### 10.6 Visual field-cue

A visual field-cue is the embodied form of the cue. It is not mere rendering. It should eventually let the human see how inherited source pressure moves, interferes, enters, fails, bends, resonates, circulates, or is blocked.

The visual field-cue is a real horizon. It is not authorized as full implementation by FieldCueV0.

## 13. Field participation statuses

Every field-cue must classify field participation instead of implying it.

Allowed participation statuses:

```txt
available;
candidate-only;
weak;
saturated;
sensitive;
degenerate;
unsupported;
misleading-risk;
not-yet-computed;
not-applicable.
```

These statuses are not excuses. They are part of the cue.

If field-world participation is weak, that is information.

If a candidate stack is saturated, that is information.

If a child’s emission tuple collapses into its antipode, that is information.

If a nearby gate candidate cannot yet justify “blocks,” that is information.

If the field contributes no useful naming pressure for a site in the current event, that is information.

FieldCueV0 must not be forced to speak beyond evidence. It must also not hide that the mature cue demands more than V0 can yet give.

## 14. Candidate-reference to field-participation ladder

The following promotion ladder is binding.

```txt
candidate reference
-> justified relation
-> field-semantic role profile
-> mature field participation
-> mature field-cue relation
```

A candidate reference only says:

```txt
this feature candidate is relevant enough to mention near this site
```

A justified relation says:

```txt
the site and feature have an evidenced relation of this kind
```

A field-semantic role profile says:

```txt
the feature plays this role inside the field ecology
```

Mature field participation says:

```txt
the child-source’s emitted behavior participates in that feature or relation in this evidenced way
```

A mature field-cue relation says:

```txt
this relation is strong enough to become part of the generated-site field biography
```

No branch may skip this ladder by prose.

No UI may display a candidate reference as if it were mature participation.

No report may call something a gate, route, loop, region, or vortex in a mature sense unless the evidence and maturity status justify that use.

## 16. Naming pressure

A field-cue must end in naming pressure, not naming conclusion.

Naming pressure is the field’s way of asking the human a sharper question.

It may include pressures such as:

```txt
inheritance pressure;
dominance pressure;
mixture pressure;
cancellation pressure;
route pressure;
gate pressure;
region pressure;
loop pressure;
phase pressure;
antipodal pressure;
sibling-contrast pressure;
degeneracy warning;
unsupported warning;
misleading-risk warning.
```

A field-cue may ask:

```txt
Does this site ask to be read as mediation, blockage, residue, carried pressure, suspended ambiguity, or transformed inheritance?

Is the child’s inherited signature stronger than its outward field behavior, or does the field-world transform the inherited signature?

Does the antipodal echo matter for naming, or is it a degeneracy of the active profile system?

Is the site supported by a region, blocked by a gate, carried by a route, trapped by a loop, disturbed by a vortex, or merely locally intense without larger field-world consequence?
```

A field-cue may not answer:

```txt
This site is concept X.
```

The human may answer. The system may preserve the answer under a separately authorized naming workflow.

## 17. Relationship to generated-site reading

A generated-site reading is the central folded object of the Event Legibility Pivot.

A field-cue is one witness inside that reading.

The other witnesses may include:

```txt
geometric lineage;
operation history;
source edge;
cell / face context;
atomic birth-law;
dual or correspondence context;
human naming notes;
later semantic handoff state.
```

The field-cue must not swallow those witnesses.

The field-cue must not become the whole interpretive object.

The correct relation is:

```txt
generated-site reading = site-centered interpretive frame
field-cue = field witness inside that frame
```

A strong field-cue makes the generated-site reading more alive. It does not replace the reading.

## 18. Relationship to topology

A field-cue is not topology.

It may eventually provide constraints, supports, routes, gates, or field-feature roles that later topology can import or test. That is a horizon, not a current permission.

No FieldCueV0 work may require topology.

No field-cue may claim that a field support is a topological support unless a topology process has actually imported and transformed material under its own rules.

No topology branch may begin merely because a field-cue contract names supports, routes, gates, regions, or phase transformations.

Topology begins only when named generated material raises a concrete topological question.

The field-cue must preserve provenance and ambiguity so that future topology is not fed lies.

---

## 19. Relationship to packets and naming state

A field-cue is not a packet.

A field-cue may later be cited by a human naming session as evidence. That does not make the field-cue a packet write.

No FieldCueV0 may silently write into vertex packets, generated-site packets, operation history, or shape genealogy.

If a later naming workflow stores human names, it must do so under its own explicit contract. The field-cue may supply evidence references and pressure summaries, but it must not create final conceptual assignments.

## 21. Branch permission test

A field-cue branch is permitted only if it satisfies one primary condition and all negative conditions.

Primary condition:

```txt
The branch makes a generated Ambo child site more legible to the human
OR
it directly clarifies the target / V0 / generalization boundary needed for that legibility.
```

Negative conditions:

```txt
no new field-feature family;
no topology dependency;
no packet write;
no Shape mutation;
no historical operation registration;
no mature-feature claim from candidate evidence;
no general-field claim from one-Ambo tetrahedron evidence;
no raw diagnostic dump as product fruit;
no source-profile variant unless directly required for the proving event;
no visual expansion that outruns the cue’s evidential status;
no displacement of human naming authority.
```

If a branch cannot pass this test, it is not a field-cue branch.

If a branch passes only because of clever wording, it is not a field-cue branch.

If a branch makes a generated site more legible without lying about maturity, it may be valid even if it is small.

## 22. FieldCueV0 success criteria

FieldCueV0 succeeds if, for the proving event, the system can produce one field-cue approximation per generated midpoint child and each cue can help the human inspect:

```txt
what the child inherited;
what emission status the child has;
what degeneracy or fallback exists;
what candidate field participation is available;
what field participation is not yet available;
what warnings matter;
what field pressure, if any, sharpens the naming question.
```

The decisive success test is not candidate count.

It is not visual density.

It is not how many routes, gates, regions, loops, or vortices appear.

The decisive test is:

```txt
Does the cue help the human read the generated site better than geometry alone?
```

If the answer is yes, the field has borne first fruit.

If the answer is no, the field-cue must reveal why: missing participation, weak feature ecology, degenerate source profile, oversaturated candidates, insufficient visual grammar, or wrong source-policy assumptions.

Even failure can be fruit if it tells the truth.

## 23. Generality after first fruit

FieldCueV0 does not authorize generalization.

After the proving event bears fruit, the project may choose one bounded portability test. Not all shapes. Not all generations. Not topology. One test.

Possible portability tests include:

```txt
same tetrahedral seed, one deeper generation;
different seed, same operation;
same generated-site cue idea, different local domain;
same field-cue object, different source-profile setup;
field-world participation maturation for one feature family only.
```

The purpose of a portability test is not feature accumulation. It is to learn what survives beyond the event-bound prototype.

The mature field-cue horizon remains vast. The path toward it must proceed through proofs of legibility, not through accumulation of machinery.

## 24. Ratification compact

The field-cue is the field’s oath to the generated site.

It says:

```txt
I will not merely compute around you.
I will tell what field signature you inherited.
I will tell how you became a source.
I will tell where your pressure travels, fails, bends, echoes, cancels, gathers, or is blocked.
I will tell which field structures answer you and what roles they play.
I will tell what I cannot yet know.
I will not name you.
I will help the human see what may dwell in you.
```

The field-cue must be mad enough to keep the whole field horizon alive: inheritance, routes, gates, regions, loops, vortices, phase transformations, interference movement, and field-world biography.

It must be disciplined enough to keep every claim scoped, evidenced, and status-marked.

The project does not need a smaller dream.

It needs the dream to pass through generated-site legibility.
